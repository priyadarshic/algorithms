Order Service — Domain Model

Order.javaJAVA 21
@Entity
@Table(name = "orders")
@Data                     // Lombok: generates getters, setters, toString
@NoArgsConstructor
public class Order {

  @Id
  @GeneratedValue(strategy = GenerationType.UUID)
  private String id;

  @Column(nullable = false)
  private String userId;

  @OneToMany(cascade = CascadeType.ALL, fetch = FetchType.EAGER)
  private List<OrderItem> items;

  @Enumerated(EnumType.STRING)
  private OrderStatus status = OrderStatus.PENDING;

  private BigDecimal totalAmount;

  @CreationTimestamp
  private LocalDateTime createdAt;
}

@Entity
@Data
@NoArgsConstructor
public class OrderItem {
  @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;
  private String  productId;
  private Integer quantity;
  private BigDecimal unitPrice;
}

public enum OrderStatus {
  PENDING, CONFIRMED, SHIPPED, DELIVERED, CANCELLED
}

Order Service — REST Controller

OrderController.javaJAVA 21
@RestController
@RequestMapping("/api/v1/orders")
@RequiredArgsConstructor
public class OrderController {

  private final OrderService orderService;

  @PostMapping
  public ResponseEntity<OrderResponse> createOrder(
      @RequestBody @Valid OrderRequest request,
      @RequestHeader("X-User-Id") String userId) {

    OrderResponse response = orderService.createOrder(request, userId);
    return ResponseEntity.status(HttpStatus.CREATED).body(response);
  }

  @GetMapping("/{id}")
  public ResponseEntity<OrderResponse> getOrder(@PathVariable String id) {
    return ResponseEntity.ok(orderService.findById(id));
  }

  @GetMapping("/user/{userId}")
  public ResponseEntity<List<OrderResponse>> getUserOrders(
      @PathVariable String userId) {
    return ResponseEntity.ok(orderService.findByUser(userId));
  }

  @PatchMapping("/{id}/status")
  public ResponseEntity<OrderResponse> updateStatus(
      @PathVariable String id,
      @RequestBody StatusUpdateRequest req) {
    return ResponseEntity.ok(orderService.updateStatus(id, req.status()));
  }
}

Order Service — Business Logic + Kafka Event

OrderService.javaJAVA 21
@Service
@RequiredArgsConstructor
public class OrderService {

  private final OrderRepository    orderRepo;
  private final ProductServiceClient productClient;  // Feign client
  private final KafkaTemplate<String, OrderEvent> kafka;
  private final OrderMapper          mapper;

  @Transactional
  public OrderResponse createOrder(OrderRequest req, String userId) {
    // 1. Verify product stock via Product Service (Feign HTTP call)
    req.items().forEach(item -> {
      ProductDto product = productClient.getProduct(item.productId());
      if (product.stock() < item.quantity()) {
        throw new InsufficientStockException(item.productId());
      }
    });

    // 2. Build and persist the order
    Order order = mapper.toEntity(req);
    order.setUserId(userId);
    order.setStatus(OrderStatus.CONFIRMED);
    Order saved = orderRepo.save(order);

    // 3. Deduct stock asynchronously via Product Service
    productClient.decrementStock(req.items());

    // 4. Publish Kafka event → Notification Service picks this up
    kafka.send("order.created",
      saved.getId(),
      new OrderEvent(saved.getId(), userId, saved.getTotalAmount())
    );

    return mapper.toResponse(saved);
  }
}

// ── Feign client (auto-discovers via Eureka) ──
@FeignClient(name = "product-service")
public interface ProductServiceClient {
  @GetMapping("/api/v1/products/{id}")
  ProductDto getProduct(@PathVariable String id);

  @PostMapping("/api/v1/products/stock/decrement")
  void decrementStock(@RequestBody List<OrderItemRequest> items);
}

CHAPTER 03 · DOCKER

Containerizing Every Service

Each Spring Boot service gets its own optimized multi-stage Dockerfile. We'll also wire everything together with Docker Compose for local development.

Multi-Stage Dockerfile (used by all services)

WHY MULTI-STAGE Stage 1 uses a full JDK to build the JAR. Stage 2 uses a minimal JRE to run it. The final image is ~200MB instead of ~700MB — no build tools, no source code.
Dockerfile (order-service)DOCKERFILE
# ═══════════════════════════════════════════════════
# STAGE 1 — Build: Maven + JDK 21
# ═══════════════════════════════════════════════════
FROM eclipse-temurin:21-jdk-alpine AS builder

WORKDIR /build

# Copy dependency manifests first for layer caching
COPY pom.xml .
COPY .mvn .mvn
COPY mvnw .
RUN chmod +x mvnw

# Download deps (cached unless pom.xml changes)
RUN ./mvnw dependency:go-offline -B -q

# Copy source and build
COPY src ./src
RUN ./mvnw package -DskipTests -B -q

# Extract layered JAR for better Docker caching
RUN java -Djarmode=layertools \
    -jar target/*.jar extract \
    --destination /build/layers

# ═══════════════════════════════════════════════════
# STAGE 2 — Runtime: minimal JRE 21
# ═══════════════════════════════════════════════════
FROM eclipse-temurin:21-jre-alpine

# Non-root user for security
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

WORKDIR /app

# Copy layered JAR contents (most-stable layers first)
COPY --from=builder /build/layers/dependencies .
COPY --from=builder /build/layers/spring-boot-loader .
COPY --from=builder /build/layers/snapshot-dependencies .
COPY --from=builder /build/layers/application .

EXPOSE 8083

# JVM tuning for containers
ENV JAVA_OPTS="-XX:+UseContainerSupport \
               -XX:MaxRAMPercentage=75.0 \
               -XX:+UseG1GC \
               -Djava.security.egd=file:/dev/./urandom"

ENTRYPOINT ["sh", "-c", \
  "java $JAVA_OPTS org.springframework.boot.loader.JarLauncher"]
LAYERED JARS Spring Boot's layertools splits the JAR into: dependencies (rarely change), spring-boot-loader (rarely change), snapshot-dependencies, and application code (changes every build). Docker rebuilds only the changed layers — cutting push/pull time dramatically.

Deep Dive: Critical K8s Settings

For a new learner, some keys in a YAML manifest seem like "boilerplate," but they are the difference between a self-healing cluster and a cascading failure. Here are the most important ones explained.

1. Probes (The Doctor)

Liveness: "Am I alive?" If this fails, K8s kills the pod and starts a new one (Reboot). Use this for deadlocks.
Readiness: "Am I ready for traffic?" If this fails, K8s stops sending requests to this pod (Isolate). Use this during slow Spring Boot startup.

2. Requests vs Limits

Requests: The minimum resources (CPU/RAM) K8s guarantees the pod. If the node doesn't have this, the pod won't start (Pending).
Limits: The absolute maximum. If a pod hits its RAM limit, it's OOMKilled. For CPU, it's just throttled (slowed down).

Graceful Shutdown & Signal Handling

When you delete a pod (or scale down), K8s sends a SIGTERM signal. By default, it waits 30 seconds (terminationGracePeriodSeconds) before sending a SIGKILL.

  • Spring Boot 3+: Set server.shutdown: graceful in application.yml so your app finishes active REST requests before exiting.
  • Pre-stop Hook: Sometimes used to wait for Nginx/LoadBalancer to stop sending traffic before the app starts shutting down.

ImagePullPolicy: Why "Always" is risky

Always: K8s pulls the image from the registry every time a pod starts. If the registry is down, your app won't start.
IfNotPresent: (Best for Prod) Only pulls if the image doesn't exist on the Node. Faster startup and more resilient.

Deployment Specs (snippet)YAML
spec:
  template:
    spec:
      containers:
      - name: order-service
        image: myapp/order-service:1.0
        imagePullPolicy: IfNotPresent
        resources:
          requests:
            memory: "512Mi"
            cpu: "250m"
          limits:
            memory: "1Gi"
        livenessProbe:
          httpGet: { path: /actuator/health/liveness, port: 8083 }
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet: { path: /actuator/health/readiness, port: 8083 }
      terminationGracePeriodSeconds: 45

How to Verify and Debug These Settings

K8s won't always tell you why a pod is failing unless you know where to look. Use these commands to inspect the settings we just discussed:

  • Check for OOMKilled or CrashLoopBackOff:
    kubectl get pods -n ecommerce — If RESTARTS > 0, your pod is likely hitting a memory limit (OOMKilled).
  • See Probe failures and Events:
    kubectl describe pod [pod-name] -n ecommerce — Look at the Events section at the bottom. It will say "Liveness probe failed" or "Readiness probe failed".
  • Monitor Resource Usage live:
    kubectl top pod -n ecommerce — Shows exactly how much CPU/RAM your pods are consuming vs their Requests/Limits.

07

Roll out an update (zero downtime)

Update the order-service to v1.3.0. K8s performs a rolling update — old pods stay alive until new ones pass health checks.

terminalBASH
# Build and tag new version
docker build -t myapp/order-service:1.3.0 ./order-service/

# Update deployment image
kubectl set image deployment/order-service \
  order-service=myapp/order-service:1.3.0 \
  -n ecommerce

# Watch the rolling update live
kubectl rollout status deployment/order-service -n ecommerce

# View rollout history
kubectl rollout history deployment/order-service -n ecommerce

# Emergency rollback if something breaks
kubectl rollout undo deployment/order-service -n ecommerce
PART B — CI/CD PIPELINE (GITHUB ACTIONS)
.github/workflows/deploy.ymlYAML
name: Build → Push → Deploy

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_PREFIX: ghcr.io/${{ github.repository_owner }}/ecommerce

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: temurin
          cache: maven
      - name: Run unit tests
        run: ./mvnw test -B
      - name: Run integration tests
        run: ./mvnw verify -P integration-test -B

  build-push:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    strategy:
      matrix:
        service: [user-service, product-service,
                  order-service, notification-service,
                  api-gateway]
    steps:
      - uses: actions/checkout@v4
      - name: Log in to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Build and push ${{ matrix.service }}
        uses: docker/build-push-action@v5
        with:
          context: ./${{ matrix.service }}
          push: true
          tags: |
            ${{ env.IMAGE_PREFIX }}/${{ matrix.service }}:latest
            ${{ env.IMAGE_PREFIX }}/${{ matrix.service }}:${{ github.sha }}

  deploy:
    needs: build-push
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - name: Set kubeconfig
        run: echo "${{ secrets.KUBECONFIG }}" | base64 -d > kubeconfig.yaml
      - name: Deploy to Kubernetes
        env:
          KUBECONFIG: ./kubeconfig.yaml
          IMAGE_TAG: ${{ github.sha }}
        run: |
          # Update image tags in manifests using kustomize
          kustomize edit set image \
            order-service=${{ env.IMAGE_PREFIX }}/order-service:$IMAGE_TAG
          kubectl apply -k k8s/overlays/production
          kubectl rollout status deployment -n ecommerce --timeout=10m
PRODUCTION CHECKLIST Before going to production: enable Pod Disruption Budgets, configure resource quotas per namespace, use Sealed Secrets (not plain Secrets in Git), set up Prometheus + Grafana for observability, configure cluster autoscaling, and use imagePullPolicy: IfNotPresent with pinned image digests instead of :latest.

FINAL CHAPTER · ANSWER KEY

Answer Key & Explanations

Check your answers against the expert solutions and dive deep into the reasoning behind each concept.

Q1. ANSWER: B

@RestController is a convenience annotation that combines @Controller and @ResponseBody. Every method return value is automatically serialized to JSON and written directly to the response body.

CONCEPT: @RestController for APIs, @Controller for Views.
Q2. ANSWER: B

Any checked exception triggers a full rollback of the database transaction due to @Transactional. However, Kafka writes are outside this boundary, necessitating pattern like the Transactional Outbox for true consistency.

CONCEPT: Transaction boundaries do not include external message brokers by default.
Q3. ANSWER: B

By copying pom.xml first and downloading dependencies, Docker creates a cached layer. This layer is reused as long as dependencies don't change, significantly speeding up subsequent builds.

CONCEPT: Docker Layer Caching — Order from least volatile to most volatile.
Q4. ANSWER: B

The service_healthy condition ensures the dependent service only starts after the healthcheck passes, not just when the container starts. This prevents connection-refused errors during boot.

CONCEPT: depends_on with healthchecks for robust orchestration.
Q5. ANSWER: B

Each COPY creates a separate layer. Since dependencies change rarely and app code changes often, Docker only needs to push the small app layer on most updates, saving bandwidth and time.

CONCEPT: Spring Boot Layered JARs for optimized CI/CD.
Q6. ANSWER: B

Failures in the readinessProbe remove the Pod from Service endpoints (no traffic). The Pod remains running as long as the livenessProbe passes. Liveness failures trigger restarts.

CONCEPT: Readiness (traffic) vs. Liveness (process health).
Q7. ANSWER: C

maxUnavailable: 0 ensures capacity never drops. maxSurge: 1 allows one extra pod. This results in a rolling update where new pods are verified healthy before old ones are removed.

CONCEPT: Achieving Zero-Downtime deployments.
Q8. ANSWER: C

When keys conflict across multiple envFrom sources, the last listed source wins. This allows for hierarchical configuration where sensitive Secrets override non-sensitive defaults.

CONCEPT: Environment variable precedence in Kubernetes.
Q9. ANSWER: B

Memory is a non-compressible resource. When a container exceeds its limit, it is immediately OOMKilled by the kernel. CPU, being compressible, is throttled instead.

CONCEPT: Memory Limits vs. CPU Throttling.
Q10. ANSWER: B

The ${variable:default} syntax allows the same image to run across local, compose, and K8s environments by resolving dynamic values at runtime from environment variables.

CONCEPT: Externalized configuration (12-Factor App).
Q11. ANSWER: A

imagePullPolicy: Always forces the kubelet to check the registry for every Pod start, ensuring the absolute latest version is run even if a local cache exists.

CONCEPT: Controlling image pull behavior.
Q12. ANSWER: C

kubectl apply is declarative and idempotent. It patches the existing resource to match the desired state defined in the YAML file without recreation.

CONCEPT: Declarative reconciliation.
Q13. ANSWER: C

The HPA uses the formula: ceil(currentReplicas * (currentMetric / targetMetric)). Here: ceil(3 * (210% / 70%)) = 9 pods. No capping occurs as it's within the 2-10 range.

CONCEPT: Understanding HPA scaling logic.
Q14. ANSWER: C

Kafka uses consumer group offsets to track progress. On restart, the consumer resumes from the last committed offset, ensuring at-least-once delivery semantics.

CONCEPT: Kafka consumer offset management.
Q15. ANSWER: B

The reclaimPolicy: Retain ensures that even if the PVC is deleted (which happens when a namespace is deleted), the underlying PersistentVolume and its data are preserved.

CONCEPT: Data persistence and reclaim policies.
